# Модель данных

Хранилище — один файл SQLite через встроенный `node:sqlite`. Режим WAL, `foreign_keys = ON`, `busy_timeout = 5000`. Схема задана в [`src/server/db.ts`](../src/server/db.ts), запросы — в [`src/server/store.ts`](../src/server/store.ts).

## Почему схема универсальная

Ни одна таблица и ни одна колонка не описывает конкретную воронку:

| Что меняется в конфиге | Где оказывается | Нужна миграция? |
|---|---|---|
| новый шаг, новый тип вопроса, новое условие | `funnel_versions.config_json`; ответ — новый ключ в `sessions.answers_json` | нет |
| новый результат или порядок правил | `config_json`; id результата — строка в `sessions.result_id` и в свойствах событий | нет |
| новое событие или новые свойства | строка в `events.name`, ключи в `events.properties_json`; список разрешённых событий берётся из конфига | нет |
| новый эксперимент или вариант | строки в `sessions.experiment_id` и `sessions.variant`, их копии в `events` | нет |

Вторая итерация это подтверждает: v3 добавляет два шага, два результата и одно событие, а схема не меняется ([`iteration-2.md`](iteration-2.md)).

## Таблицы

```
funnel_versions 1 ──< activations       (история активаций, append-only)
funnel_versions 1 ──< sessions          (sessions.version — внешний ключ)
sessions        1 ──< events            (логическая связь; проверяется при приёме, FK нет)
ingest_batches                          (по строке на каждый POST /api/events)
```

### `funnel_versions`

| Колонка | Смысл |
|---|---|
| `version` PK | номер из самого конфига (`config.version`) |
| `funnel_id`, `title` | из конфига, для списков |
| `config_json` | конфиг целиком, после разбора zod-схемой и без файлового поля `status` |
| `status` | `draft`, `published` или `rolled_back` |
| `release_note` | `releaseNote` из конфига, показывается в админке |
| `created_at`, `published_at` | время загрузки и первой публикации |

Версии неизменяемы: конфиг после загрузки не редактируется. Поэтому сервер держит разобранные конфиги в памяти (`configFor(version)`) без инвалидации.

### `activations`

| Колонка | Смысл |
|---|---|
| `id` | порядок записей |
| `version` | версия, которую затронуло действие |
| `action` | `seed`, `publish`, `activate` или `rollback` |
| `from_version` | какая версия была активной до действия |
| `at` | время |

### `sessions`

| Колонка | Смысл |
|---|---|
| `id` PK | `randomUUID()` сервера |
| `funnel_id`, `version`, `experiment_id`, `variant`, `assignment_source` | закрепляются при создании и больше не меняются |
| `utm_source`, `utm_medium`, `utm_campaign` | first touch из URL при создании сессии (пустые строки превращаются в `NULL`) |
| `run_id` | метка прогона генератора; UI её не ставит; используется как фильтр аналитики |
| `answers_json` | ответы по ключу `step.input.name` |
| `current_step_id` | текущий шаг; его хранит сервер, а не клиент |
| `result_id` | посчитанный сервером результат; сбрасывается, если меняется какой-либо ответ |
| `created_at`, `updated_at`, `expires_at` | `expires_at = created_at + ttlHours` |

### `events`

| Колонка | Смысл |
|---|---|
| `event_id` PK | от клиента; первичный ключ обеспечивает идемпотентность |
| `session_id`, `name`, `step_id` | что произошло и где |
| `funnel_id`, `funnel_version`, `experiment_id`, `variant` | копия контекста из сессии, а не значения от клиента |
| `utm_source`, `utm_medium`, `utm_campaign` | копия из сессии |
| `client_ts`, `server_ts` | время клиента (у `session_started` — `NULL`) и время приёма пачки |
| `properties_json` | только свойства из белого списка закреплённой версии |

Порядок поступления — неявный `rowid`; аналитика читает его как `seq`. Индексы: `events(session_id)` и `events(funnel_version, variant)`.

Контекст продублирован в каждом событии намеренно. Событие самодостаточно, его нельзя приписать чужой версии или варианту, и оно не зависит от ответов, которые обнуляются после TTL.

### `ingest_batches`

По строке на каждый запрос `POST /api/events`: `received_at`, `total`, `accepted`, `duplicates`, `rejected`. Из этих строк берутся показатели `duplicatesDropped` и `rejectedEvents` в блоке качества данных. Повторная отправка пачки после таймаута тоже видна здесь: её элементы попадают в `duplicates`.

## Версии, стек активаций и статусы

Активная версия хранится не в отдельном поле, а вычисляется проигрыванием журнала `activations` как стека: `seed`, `publish` и `activate` кладут версию на стек, `rollback` снимает верхнюю. Активна верхняя версия стека, цель отката — версия под ней. Журнал только дополняется, поэтому история публикаций и откатов не теряется.

| Действие | Условие | Статусы | Стек |
|---|---|---|---|
| загрузка или импорт фикстуры | конфиг проходит `parseFunnelConfig`, номера ещё нет и он больше всех сохранённых | новая версия получает `draft` | не меняется |
| `publish` | версия в статусе `draft` | `published`, ставится `published_at` | push |
| `rollback` | на стеке не меньше двух записей, иначе `409 nothing_to_rollback` | снятая версия получает `rolled_back`, цель — `published` | pop |
| `activate` | версия не `draft` и не активна сейчас | `published` | push |

Пример: `seed 1` → `[1]`; `publish 3` → `[1, 3]`, активна v3; `rollback` → `[1]`, активна v1, v3 в статусе `rolled_back`; `activate 3` → `[1, 3]`, активна v3.

Откат ничего не удаляет. Сессии откатанной версии продолжают работать на ней, её события остаются в аналитике.

Новые сессии создаются только на активной версии. Если активной версии нет, `POST /api/sessions` отвечает `503 no_active_version`; после seed такого не бывает.

## Сессии

- **Закрепление.** `version`, `experiment_id`, `variant` и `assignment_source` записываются в `INSERT` и не входят в `UPDATE` (`updateSessionProgress` меняет только ответы, текущий шаг, результат и `updated_at`). Каждый запрос к сессии разрешает воронку по закреплённой версии: `resolveFunnel(configFor(session.version), session.variant)`.
- **Возобновление.** `POST /api/sessions` с `sessionId` возвращает ту же сессию (`resumed: true`), если она существует, не истекла и либо override не задан, либо он совпадает с её вариантом. В остальных случаях создаётся новая сессия на активной версии.
- **Назначение варианта.** Берутся первые 8 hex-символов `sha256(experimentId + ':' + sessionId)`, делятся на 2^32 и раскладываются по кумулятивным весам вариантов, отсортированных по ключу ([`src/server/assignment.ts`](../src/server/assignment.ts)). Так как назначение детерминировано, вариант можно пересчитать, но хранится он всё равно в сессии.
- **Override.** Значение `?variant=X` принимается, только если `X` — ключ варианта активной версии. Тогда `assignment_source = 'override'`. Неизвестное значение игнорируется, и вариант назначается по хешу.
- **TTL от создания.** `expires_at = created_at + ttlHours` по конфигу версии, на которой создана сессия. Активность срок не продлевает. Истёкшая сессия отвечает `410 session_expired`, и клиент создаёт новую.
- **Очистка ответов.** При старте и затем раз в час `purgeExpiredAnswers` ставит `answers_json = '{}'` всем истёкшим сессиям. Строка сессии и её события остаются. Для запроса есть индекс `sessions(expires_at)`.
- **Скрытые ответы.** Если пользователь вернулся и изменил ответ так, что шаг стал скрыт, ответ на скрытый шаг остаётся в `answers_json` (он подставится, если шаг снова станет видимым). На видимость, полноту и результат он не влияет: движок считает всё по «эффективным» ответам видимых шагов.
- **Сырые ответы** живут только в `sessions.answers_json`. Они нужны, чтобы продолжить воронку и посчитать результат, и после TTL обнуляются. В событиях и аналитике их нет ([`events.md`](events.md#приватность)).

## Миграции

Миграции — упорядоченный массив SQL-скриптов `MIGRATIONS` в [`src/server/db.ts`](../src/server/db.ts). Номер применённой миграции хранится в `PRAGMA user_version`. При открытии базы применяются скрипты с индексом от `user_version` до конца массива, каждый в своей транзакции `BEGIN IMMEDIATE` вместе с обновлением `user_version`.

| № | Что делает |
|---|---|
| 1 | все пять таблиц и индексы `events` |
| 2 | индекс `sessions(expires_at)` для очистки |

Новая миграция добавляется в конец массива; применённые скрипты не редактируются. Изменения конфигов, включая вторую итерацию, миграций не требуют.

Файл базы задаётся через `DB_PATH` (по умолчанию `./data/funnel.db`; каталог создаётся при старте). При деплое файл должен лежать на постоянном диске, иначе версии и аналитика пропадут при перезапуске.
