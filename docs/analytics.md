# Аналитика

`GET /api/analytics` вызывает чистую функцию `computeAnalytics` ([`src/server/analytics.ts`](../src/server/analytics.ts)). На вход она получает строки сессий, строки событий с порядком поступления (`seq` = `rowid`), разобранные конфиги всех версий, итоги `ingest_batches` и фильтры. Функция не обращается ни к HTTP, ни к БД, поэтому [`tests/analytics.test.ts`](../tests/analytics.test.ts) кормит её строками напрямую.

Параметры запроса: `utm_campaign`, `version`, `run_id`, `include_overrides=1`. Dashboard ([`/dashboard`](../src/client/pages/DashboardPage.tsx)) показывает те же правила кратко в блоке «How these numbers are calculated».

## Главный принцип

Каждое число — это размер множества уникальных сессий. Для каждой сессии строятся множества: каких шагов она достигла, какой шаг для неё самый дальний, был ли результат, был ли клик по CTA. Только после этого сессии считаются. Количество событий используется лишь в колонке `views` и в блоке качества данных.

## Популяция

- Сессии фильтруются по полям самой сессии: `version` (закреплённая версия), `utm_campaign` (first touch) и `run_id`. Фильтры комбинируются.
- `utm_campaign=(none)` (константа `NO_CAMPAIGN` в [`src/shared/api.ts`](../src/shared/api.ts)) выбирает сессии, у которых `utm_campaign IS NULL`. На dashboard это пункт «(no campaign)».
- В расчёт идут только события сессий из популяции.
- **Started** — число сессий в популяции. Каждая сессия создаётся в одной транзакции со своим `session_started`, поэтому это одно и то же.
- Списки `available.campaigns` и `available.versions` для фильтров строятся по всем сессиям, без учёта фильтров. В `available.campaigns` сначала идут названные кампании по алфавиту, а `(none)` — последней и только если есть хотя бы одна сессия без кампании. Кампания с буквальным именем `(none)` отдельным пунктом не показывается, а фильтр `(none)` её не выбирает: он берёт только сессии без кампании.

## Воронка по шагам

Воронка строится для каждой пары (версия, вариант) в порядке `stepSequence` этого варианта.

| Понятие | Правило |
|---|---|
| прямое достижение | у сессии есть `step_viewed`, `answer_submitted`, `step_completed` или `back_clicked` с этим `step_id` |
| первый шаг (интро) | достигнут всеми начавшими сессиями |
| шаг результата | достигнут, если есть `result_viewed`, `cta_clicked` или `recommendation_expanded` |
| `furthest` | наибольший индекс шага среди прямо достигнутых |
| подразумеваемое достижение | безусловный шаг (без `visibleWhen`) с индексом меньше `furthest` считается достигнутым, даже если его событие потерялось |
| условный шаг | засчитывается только по собственным событиям |
| `reached` | число сессий, достигших шага |
| `progressed` | достигли шага, и `furthest` дальше него |
| `dropped` | достигли шага, и `furthest` равен ему |
| `conversion` | `progressed / reached`: доля ушедших дальше этого шага |
| `dropOffRate` | `dropped / reached` |
| строка результата | `reached` — достигли результата, `progressed` — кликнули CTA, `dropped` — остальные; её `conversion` равна CTR |
| `views` | сырое число событий `step_viewed` на шаге, вместе с повторами |

`conversion` — это доля ушедших дальше, а не отношение следующей строки к текущей. Из-за условных шагов `reached` следующей строки может быть меньше, хотя никто не отвалился: шаг `office_days` видят только гибридные и офисные команды.

Условные шаги не подразумеваются, потому что их видимость зависит от сырых ответов, которых в аналитике нет. Иначе удалённая команда числилась бы прошедшей `office_days`.

Override-сессии в воронки, итоги и сравнение версий входят. Исключаются они только из A/B-сравнения (см. ниже).

## KPI

| Показатель | Формула |
|---|---|
| `started` | сессии в популяции |
| `reachedResult` | сессии с `result_viewed`, `cta_clicked` или `recommendation_expanded` |
| `resultRate` | `reachedResult / started` |
| `ctaClicked` | сессии хотя бы с одним `cta_clicked` |
| `ctr` | `ctaClicked / reachedResult` |
| `startedToCta` | `ctaClicked / started` — основная метрика эксперимента |

Если знаменатель равен нулю, доля равна `null` (на dashboard отображается как «—»). KPI считаются по всей популяции (`totals`) и по каждой версии (`versions`). У разных версий разные шаги, поэтому версии сравниваются только по этим не зависящим от шагов KPI.

## A/B-сравнение

- Сравнение идёт внутри одной версии. У каждой версии свой `experiment.id`, и сессии разных версий не смешиваются.
- Сессии с `assignment_source = 'override'` исключаются, если не передан `include_overrides=1`. Их число отдаётся как `excludedOverrideSessions`.
- Метрика — `startedToCta` по варианту. `absoluteDiff = B − A`; `relativeLift = absoluteDiff / A` (`null`, если A = 0).
- p-value считается двусторонним z-тестом для двух долей с объединённой оценкой:

  ```
  p̂ = (x_A + x_B) / (n_A + n_B)
  SE = sqrt(p̂ · (1 − p̂) · (1/n_A + 1/n_B))
  z  = (x_B/n_B − x_A/n_A) / SE
  p  = 2 · Φ(−|z|)
  ```

  Φ вычисляется через `erf` в приближении Абрамовица–Стиган 7.1.26 (погрешность меньше 1.5e-7). `significant = p < 0.05`. Тест считается только для ровно двух вариантов.

- **Минимальная выборка.** p-value считается, только если в **каждом** варианте `n · p̂ ≥ 5` и `n · (1 − p̂) ≥ 5`, где `p̂` — объединённая доля started → CTA обоих вариантов. То есть в каждом варианте ожидается не меньше 5 кликов и 5 не-кликов. Проверка идёт в целых числах. Ниже порога `pValue` и `significant` равны `null`, а `absoluteDiff` и `relativeLift` всё равно отдаются; карточка на dashboard пишет «not enough data yet». Случай SE = 0 (объединённая доля 0 или 1) этим правилом тоже покрыт.

## Распределение результатов

Для каждой (версии, варианта, `result_id`) считается число сессий, у которых последнее событие `result_viewed` несёт этот `result_id`. Последнее определяется по `client_ts`, а при равенстве — по порядку поступления. Сессия, которая вернулась, изменила ответ и получила другой результат, учитывается один раз, с последним результатом.

## Качество данных

| Показатель | Как считается |
|---|---|
| `eventsStored` | события популяции, включая `session_started` |
| `duplicatesDropped` | сумма `duplicates` по `ingest_batches` (глобально, без фильтров) |
| `rejectedEvents` | сумма `rejected` по `ingest_batches` (глобально) |
| `repeatedStepViews` | число `step_viewed` минус число различных пар (сессия, шаг) |
| `backClicks` | число событий `back_clicked` |
| `outOfOrderEvents` | события, у которых `client_ts` раньше, чем у события той же сессии, пришедшего до них |
| `sessionsWithOutOfOrderEvents` | сессии хотя бы с одним таким событием |
| `events` | массив `{ name, events, sessions }` по каждому имени события в популяции: сырое число событий и число уникальных сессий, по алфавиту. Сумма `events` равна `eventsStored`, `session_started` тоже входит. На dashboard это таблица «Events by name, in this view»: в ней видно `recommendation_expanded`, когда появляется трафик v3 |

## Почему повторы, Back, дубли и порядок не искажают показатели

| Искажение | Почему не влияет |
|---|---|
| дубль `event_id` (повтор пачки, retry после таймаута) | сохраняется один раз: первичный ключ и `INSERT OR IGNORE` |
| дубль действия с разными `event_id` (двойной клик, refresh) | метрики — это принадлежность сессии к множеству, а второе событие не меняет множество |
| повторный просмотр шага | `reached` — множество; повтор виден только в `views` и `repeatedStepViews` |
| Back | `furthest` — максимум по всем событиям, возврат его не уменьшает, поэтому шаг, на который вернулись, не становится точкой отвала; `back_clicked` к тому же отмечает покинутый шаг как достигнутый |
| события не по порядку | ни одна метрика воронки и KPI не зависит от порядка. Порядок используется только в распределении результатов (по `client_ts`, затем по поступлению) и в счётчике `outOfOrderEvents` |
| потерянное событие безусловного шага | дыру закрывает подразумеваемое достижение |
| несколько кликов CTA | `ctaClicked` — множество сессий |
| некорректные события | не сохраняются, видны только в `rejectedEvents` |
| QA-трафик через `?variant=` | исключается из A/B по умолчанию |

Тесты на эти случаи: повторный просмотр, Back, доставка не по порядку, потерянные события безусловного и условного шага, место отвала. Все они в [`tests/analytics.test.ts`](../tests/analytics.test.ts).

## Известные ограничения

- Если потерялось событие условного шага, этот шаг будет недосчитан; восстановить его видимость без ответов нельзя.
- Достижение результата определяется только по событиям. `sessions.result_id` аналитика не читает. Если `result_viewed` потерялся, а клика CTA не было, сессия не попадёт в `reachedResult`.
- Сессия, которая не прислала ни одного события после `session_started`, считается отвалившейся на интро.
- Пересчёт идёт в памяти при каждом запросе. На демо-объёмах этого хватает, для продакшна нужны предагрегаты.
- Отдельного KPI для `recommendation_expanded` нет: v1 это событие не разрешает, и общий для всех версий KPI показывал бы для v1 ложный 0. Событие видно в таблице событий по имени.

## Проверка по генератору

Генератор ([`scripts/generate-traffic.ts`](../scripts/generate-traffic.ts), [`scripts/lib/simulate.ts`](../scripts/lib/simulate.ts)) ведёт для каждой сессии «истину», которая не зависит от кода аналитики:

- какие шаги сессия показала (`reached`);
- дошла ли до результата, кликнула ли CTA, какой получила `result_id`;
- сколько было показов шагов и кликов Back.

[`scripts/lib/truth.ts`](../scripts/lib/truth.ts) по этой истине считает ожидаемые итоги: по версиям, по вариантам, `reached`/`progressed`/`dropped` для каждого шага каждой воронки, распределение результатов, `repeatedStepViews`, `backClicks`, а также `outOfOrderEvents` по фактическому плану доставки после удаления дублей. Всё это сохраняется в `expected-<runId>.json`.

Доставку генератор намеренно портит:

- переставляет соседние события сессии (6% пар);
- перемешивает 15% пачек целиком;
- подмешивает копии уже отправленных событий;
- повторно отправляет каждую шестую пачку;
- добавляет четыре некорректных события: `unknown_step`, `unknown_session`, `server_only`, `invalid_event`.

После отправки генератор сверяет `accepted`, `duplicates` и `rejected` из ответов сервера со своим планом.

`npm run verify -- --expected expected-<runId>.json` запрашивает `/api/analytics?run_id=<runId>&include_overrides=1` и сравнивает итоги, каждую версию и вариант (`started`, `reachedResult`, `ctaClicked`), `reached`/`progressed`/`dropped` каждого шага каждой воронки, распределение результатов и четыре показателя качества данных (`repeatedStepViews`, `backClicks`, `outOfOrderEvents`, `sessionsWithOutOfOrderEvents`), затем повторяет запрос с фильтром по каждой кампании, включая `(none)` для трафика `direct`, и сверяет `started`. Число проверок зависит от сценария и от данных прогона. `--seed` фиксирует модель поведения, но варианты назначает сервер, поэтому каждый прогон даёт свой набор данных и сверяется со своим файлом ожидаемых агрегатов.

Прогоны 2026-10-02 (каждый сверялся по своему `run_id`):

| Где | Прогон | Результат |
|---|---|---|
| локально, при интеграции (`8c2f3ce`, до исправлений ревью; `verify` тогда ещё не сверял кампанию `(none)`) | `--scenario iteration2 --sessions 150` (v1 и v3 в одном прогоне) | 165/165 |
| локально | `--scenario simple` | 83/83 |
| публичный URL | `prod-v1`: `simple`, 150 сессий на v1 | 83/83 |

Чего эта проверка не покрывает: генератор не теряет события, и каждый шаг, по которому он идёт, сначала показывается. Поэтому подразумеваемое достижение здесь не проверяется; его покрывают модульные тесты.
