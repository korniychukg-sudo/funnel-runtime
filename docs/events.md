# События

Событие `session_started` пишет сервер. Остальные события отправляют браузер ([`src/client/events.ts`](../src/client/events.ts), [`src/client/outbox.ts`](../src/client/outbox.ts)) или генератор трафика через `POST /api/events` ([`src/server/routes/events.ts`](../src/server/routes/events.ts)). Набор разрешённых событий и их свойств задаёт конфиг версии (`events.allowed`). Проверка всегда идёт по версии, закреплённой за сессией, а не по активной.

## Формат на входе

```json
{
  "events": [
    {
      "event_id": "9f1c…",
      "session_id": "4b6e…",
      "name": "step_viewed",
      "client_timestamp": "2026-10-02T13:05:11.204Z",
      "step_id": "work_mode",
      "funnel_id": "workstyle-planner",
      "funnel_version": 1,
      "experiment_id": "question-order-and-result-framing-v1",
      "variant": "B",
      "utm_source": "google",
      "utm_medium": "cpc",
      "utm_campaign": "remote_ops_search",
      "properties": { "step_type": "single-select", "visible_step_index": 1, "visible_step_count": 7 }
    }
  ]
}
```

## Поля сохранённого события

| Поле | Откуда | Правило |
|---|---|---|
| `event_id` | клиент | строка 1–128 символов; браузер берёт 16 случайных байт в hex, генератор — UUID |
| `session_id` | клиент | сессия должна существовать |
| `name` | клиент | должно быть в `events.allowed` закреплённой версии |
| `step_id` | клиент | для шаговых событий обязателен и должен входить в `stepSequence` варианта сессии; для событий результата, если не передан, подставляется id шага результата |
| `funnel_id`, `funnel_version`, `experiment_id`, `variant` | сессия | берутся из сессии; если клиент прислал другое значение, событие отклоняется |
| `utm_source`, `utm_medium`, `utm_campaign` | сессия | всегда из сессии (first touch); значения клиента игнорируются |
| `client_ts` | клиент | `client_timestamp` в ISO-8601 с `Z` или смещением, обязателен |
| `server_ts` | сервер | время приёма запроса, одно на всю пачку |
| `properties` | клиент и сервер | остаются только ключи из списка свойств этого события в закреплённой версии, остальные молча отбрасываются. `step_type` и `answer_kind` ставит сервер. Значения проверяются (`invalid_property`, см. ниже) |

## События

| Событие | Когда отправляется | `step_id` | Свойства |
|---|---|---|---|
| `session_started` | сервер, в той же транзакции, что и создание сессии | `null` | нет; `event_id = <sessionId>:session_started`, `client_ts = null` |
| `step_viewed` | при каждом показе шага: первая загрузка, refresh, после Back; включая интро и результат | показанный шаг | `step_type` (ставит сервер), `visible_step_index` (номер среди учитываемых в прогрессе шагов; `null` у интро и результата), `visible_step_count` |
| `answer_submitted` | сервер принял ответ (200) | шаг, на который ответили | `answer_kind` — тип шага: `number`, `single-select` или `multi-select` (ставит сервер) |
| `step_completed` | сразу после `answer_submitted` | тот же шаг | `next_step_id` — следующий шаг, который вернул сервер |
| `back_clicked` | кнопка Back или Back браузера | шаг, который покидают | `destination_step_id` |
| `result_viewed` | результат показан (после `POST /api/sessions/:id/result`) | шаг результата | `result_id` |
| `cta_clicked` | клик по основному CTA результата | шаг результата | `result_id`, `action` |
| `recommendation_expanded` | только v3: CTA раскрыл список рекомендаций | шаг результата | `result_id`, `action`, `source = result_cta` |

Замечания:

- Интро — информационный шаг, ответа у него нет, поэтому `step_completed` для него не отправляется. Переход с интро виден по тому, что достигнут следующий шаг.
- `step_type` и `answer_kind` сервер берёт из типа шага после overrides варианта (`deepMerge(config.steps[id], stepOverrides[id]).type`). Значение клиента игнорируется. Если клиент свойство не прислал, сервер всё равно его добавит, когда закреплённый конфиг это свойство разрешает.
- В текущем UI CTA сам раскрывает рекомендации, поэтому в v3 `cta_clicked` и `recommendation_expanded` уходят одним кликом. Свойство `source` оставлено, чтобы различать другие точки входа, если они появятся.
- Раскрытый список запоминается в `localStorage` (`funnel.expanded.<sessionId>` = id результата). После refresh список остаётся открытым, кнопки CTA нет, и `cta_clicked` и `recommendation_expanded` повторно не отправляются.
- Надпись «Question X of N» учитывает редактируемый ответ, как только он проходит локальную валидацию. `visible_step_index` и `visible_step_count` в `step_viewed` считаются по сохранённым ответам на момент показа шага.
- Клиент отправляет только события и свойства, которые есть в `funnel.allowedEvents` его версии. Сессия v1 `recommendation_expanded` не шлёт, а если такое событие пришлёт кто-то другой, сервер отклонит его как `event_not_allowed`. На публичном URL это проверено ([`iteration-2.md`](iteration-2.md#ход-проверки-на-публичном-url)).

## Приём пачки

`POST /api/events` проверяет каждый элемент отдельно, внутри одной транзакции `BEGIN IMMEDIATE`. Некорректный элемент получает статус `rejected` с причиной и не мешает остальным.

Проверки по порядку:

| Причина | Когда |
|---|---|
| `invalid_event` | элемент не объект; нет или неверного типа `event_id`, `session_id` или `name` (строки 1–128 символов); `client_timestamp` не ISO-8601 с `Z` или смещением; `properties` не объект |
| `unknown_session` | сессии с таким id нет |
| `server_only` | `name = session_started`: это событие пишет только сервер |
| `event_not_allowed` | имени нет в `events.allowed` закреплённой версии |
| `context_mismatch` | клиент прислал `funnel_id`, `funnel_version`, `experiment_id` или `variant`, отличный от значения в сессии |
| `unknown_step` | у шагового события (`step_viewed`, `answer_submitted`, `step_completed`, `back_clicked`) нет `step_id`, или переданный `step_id` не входит в `stepSequence` варианта |
| `invalid_property` | значение оставленного свойства не прошло проверку (правила ниже) |

Правила для значений свойств. Они действуют по имени свойства для любого события, которое это свойство разрешает:

| Свойство | Допустимое значение |
|---|---|
| любое | `null`, boolean, конечное число или строка не длиннее 256 символов |
| `result_id` | строка, которая является ключом `results` закреплённой версии (`null`, `constructor` и id только из v3 для сессии v1 не проходят) |
| `next_step_id`, `destination_step_id` | строка из `stepSequence` варианта сессии |
| `visible_step_index`, `visible_step_count` | `null` или неотрицательное целое |

Ключи, которых нет в списке свойств события, по-прежнему молча отбрасываются и не проверяются.

Истёкшие сессии и сессии откатанной версии события по-прежнему принимают: поздняя доставка из outbox — нормальная ситуация.

Ответ:

```json
{
  "accepted": 2,
  "duplicates": 1,
  "rejected": 1,
  "results": [
    { "index": 0, "event_id": "a1", "status": "accepted" },
    { "index": 1, "event_id": "a1", "status": "duplicate" },
    { "index": 2, "event_id": "b7", "status": "accepted" },
    { "index": 3, "event_id": "c3", "status": "rejected", "reason": "unknown_step" }
  ]
}
```

На уровне HTTP возможны только две ошибки: `400`, если тело не имеет вида `{ events: [...] }` или в нём больше 500 элементов (`invalid_batch`; если тело вообще не разбирается как JSON — `bad_request`), и `413 payload_too_large`, если тело больше 1 МБ. Во всех остальных случаях ответ 200, а итог описан по каждому элементу. Каждый запрос добавляет строку в `ingest_batches`.

Ключи `__proto__` и `constructor.prototype` в JSON-теле любого запроса вырезаются при разборе. Раньше такой ключ в одном событии ронял всю пачку с `400`; теперь это событие обрабатывается само по себе, как любое другое.

## Идемпотентность

- `event_id` — первичный ключ, вставка идёт через `INSERT OR IGNORE`. Повтор того же id даёт `duplicate`, и побеждает первая запись, даже если в повторе другое содержимое. Это работает и для повторов внутри одной пачки.
- Пачка обрабатывается в одной транзакции, поэтому записаться наполовину она не может. Повторный запрос после таймаута безопасен. Если первый запрос успел закоммититься, повтор вернёт только `duplicate`. Если не успел, повтор запишет события. В обоих случаях в таблице окажется ровно по одной строке на `event_id`.
- Генератор проверяет это на каждом прогоне: он повторно отправляет целые пачки, подмешивает копии событий и сверяет ответы сервера со своим планом ([`analytics.md`](analytics.md#проверка-по-генератору)).

## Outbox на клиенте

| Правило | Значение |
|---|---|
| где лежит очередь | `localStorage['funnel.outbox']`; переживает refresh; если хранилище недоступно, очередь живёт в памяти |
| обычная отправка | через 1 с после последнего добавления, пачками до 50 событий; с `keepalive: true`, если тело меньше 60 000 байт (лимит keepalive в браузере около 64 КБ), иначе без него |
| уход со страницы | на `pagehide` и при переходе вкладки в `hidden` первые 50 или меньше событий очереди уходят отдельным запросом с `keepalive: true`, даже если обычная пачка ещё в полёте. Дубли при этом безвредны: `event_id` идемпотентен |
| параллельность | не больше одной обычной пачки и одного запроса при уходе одновременно |
| когда событие удаляется из очереди | только после ответа 200. Статусы `accepted`, `duplicate` и `rejected` окончательные: повтор отклонённого события результат не изменит |
| что делать при сбое | при сетевой ошибке, таймауте 10 с или любом статусе, кроме 200, события остаются в очереди; повтор с экспоненциальной задержкой 1 с → 2 с → … → 30 с; новые события не сбрасывают уже назначенную задержку; опустевшая очередь сбрасывает счётчик неудач |
| несколько вкладок | каждое сохранение перечитывает `funnel.outbox`, сохраняет события других вкладок и удаляет только те id, за которые эта вкладка получила 200. События закрытой вкладки отправит следующая загрузка страницы |
| битые данные | если сохранённая очередь не парсится, outbox начинает с пустой |

Ограничение: при уходе со страницы уходит не больше 50 событий. Остальные остаются в `localStorage` и будут отправлены при следующем открытии сайта в этом браузере.

Тесты: [`tests/outbox.test.ts`](../tests/outbox.test.ts), [`tests/events.test.ts`](../tests/events.test.ts), [`tests/client-events.test.ts`](../tests/client-events.test.ts).

## Хранилище клиента

| Ключ `localStorage` | Что лежит |
|---|---|
| `funnel.sessionId` | id текущей сессии; `?reset=1` его удаляет |
| `funnel.outbox` | очередь неотправленных событий |
| `funnel.expanded.<sessionId>` | id результата, чей список рекомендаций открыт; `?reset=1` удаляет ключ прежней сессии |
| `funnel.adminToken` | только на `/admin`: токен админки, если сервер запущен с `ADMIN_TOKEN` и спросил его |

Если клиент при загрузке отправил сохранённый `funnel.sessionId`, а сервер вернул другую, не возобновлённую сессию и она создана не через `?variant=`, клиент показывает «Your previous session has expired, so we started a new one.»

## Приватность

- В конфиге стоит `events.privacy.storeRawAnswers = false`, и это соблюдается в двух местах:
  - в `answer_submitted` есть только `answer_kind`, то есть тип шага, и его ставит сервер, поэтому сырой ответ под этим ключом сохранить нельзя;
  - сервер оставляет только ключи из белого списка закреплённой версии. Даже если клиент пришлёт `properties.value` или `properties.team_size`, в базу это не попадёт.
- Значения оставленных свойств ограничены примитивами и строками до 256 символов, `result_id` и id шагов сверяются с конфигом. Свободным текстом до 256 символов остаются только `action` и `source`.
- Сырые ответы хранятся только в `sessions.answers_json`, потому что они нужны для навигации и расчёта результата. После TTL они обнуляются. Аналитика читает события и метаданные сессий, но не `answers_json`.
- `result_id` — производная категория, а не ответ пользователя.
