# Работа с AI-агентами

Работу вёл оркестратор: основная сессия Claude Code. Он запускал субагентов волнами, сам писал контракты и общий движок, сам интегрировал результат. Правила работы:

- агенты одной волны работают с непересекающимися файлами и общим контрактом;
- результат агента принимается только после запуска: тестов, генератора, браузера, а не со слов агента;
- находки ревью проходят состязательную проверку перед исправлением.

## 1. Анализ: 6 агентов параллельно + критик

| Агент | Задача | Как использовано |
|---|---|---|
| форензика конфигов | разобрать v1 и v3 скриптом-перебором комбинаций ответов: пути через воронку в каждом варианте, видимость шагов, достижимые результаты, полный дифф v1 → v3 | модель шагов, условий и прогресса в движке; дифф в [`iteration-2.md`](iteration-2.md) |
| матрица требований | каждое требование задания → проверяемый критерий приёмки | чек-лист для контрактов и ревью соответствия |
| хостинг | варианты публичного хостинга для Node и файловой SQLite | п. 6 |
| оценка: MVP | минимальный срез, который закрывает все пункты задания | объём первой итерации |
| оценка: риски | что вероятнее всего сломается: идемпотентность, закрепление версий, порядок событий, ветвления в прогрессе | список инвариантов в контрактах и тестах |
| оценка: проверяющий | что увидит проверяющий по критериям п. 11 | приоритеты: вторая итерация, аналитика, документация |
| критик полноты | сверить выводы волны с текстом задания и найти пропуски | дополнения к плану |

Три оценки делались независимо, с разных позиций, и оркестратор свёл их в один план.

## 2. Контракты до кода

До сборки оркестратор сам написал:

- [`docs/contracts.md`](contracts.md): эндпоинты и коды ошибок, схему БД, порядок проверок при приёме событий, таблицу клиентских событий, правила аналитики, интерфейс генератора;
- `src/shared/*`: схему конфига (zod и семантические проверки), вычисление условий, `deepMerge` для overrides, движок воронки и DTO API.

Коммит `f9b5ceb`. Движок — самая связанная часть системы: его используют браузер, сервер и генератор. Поэтому он написан один раз до параллельной работы, а агенты получили готовые типы и функции вместо устных договорённостей.

## 3. Сборка: 4 агента на непересекающихся файлах

| Агент | Файлы | Свои тесты |
|---|---|---|
| сервер | `src/server/**`, кроме `analytics.ts` | `tests/sessions`, `events`, `versions`, `pinning`, `ab`, `helpers.ts` |
| аналитика и тесты движка | `src/server/analytics.ts` | `tests/analytics`, `engine`, `config`, синтетический конфиг `tests/fixtures/funnel-synthetic.json` |
| UI воронки и outbox | `src/client/funnel/*`, `src/client/api.ts`, `events.ts`, `outbox.ts` | `tests/client-events`, `outbox` |
| admin и dashboard | `src/client/pages/*`, `src/client/adminApi.ts` | `tests/client-pages.test.tsx`, `tests/fixtures/pages.ts` |

Каждый агент правил только свои файлы и сдавал работу с зелёными тестами своей части и чистым `tsc`. Если контракт требовал изменения, оно шло через оркестратора.

## 4. Интеграция: оркестратор

- Сборка частей, полный прогон `npm test` и `npm run typecheck`.
- **Дефект движка, найденный тестом агента.** Тест на синтетическом конфиге проверял цепочку условий: `bike_storage` зависит от `bike_type`, а тот — от `transport`. Тест показал, что `progressFor` продолжал считать зависимый шаг, когда шаг-источник скрыт: условие оставалось «неизвестным», и в счётчике «Question N of M» висел лишний вопрос. Исправление: ответы скрытых шагов считаются заведомо отсутствующими (тест «drops a chained conditional step whose source step is hidden» в [`tests/engine.test.ts`](../tests/engine.test.ts)). В выданных v1 и v3 цепочек условий нет, поэтому дефект поймался только благодаря третьему, синтетическому конфигу.
- **Сквозной прогон.** Сервер, `npm run generate` и `npm run verify`: 165/165 проверок совпали с ground truth генератора.
- **Браузерная проверка** страниц `/`, `/admin` и `/dashboard`.
- Коммит `8c2f3ce`.

## 5. Ревью: пять направлений, у каждого состязательный верификатор

| Направление | Что проверяется |
|---|---|
| соответствие заданию | каждое требование п. 1–9 по матрице требований |
| backend | транзакции, коды ошибок, закрепление версии, TTL, поведение при откате |
| аналитика | агрегаты против контракта, крайние случаи: нулевые знаменатели, Back, порядок, дубли |
| клиент | состояние при refresh и Back, outbox, ошибки сети, доступность |
| безопасность | токен админки, лимиты тела, приватность ответов, валидация входа |

На каждом направлении работали ревьюер и отдельный верификатор. Верификатор пытался опровергнуть каждую находку: воспроизвести её или показать, что это не дефект. Решение об исправлении принимал оркестратор, и только по подтверждённым находкам.
