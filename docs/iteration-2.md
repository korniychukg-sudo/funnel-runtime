# Вторая итерация: v1 → v3

Новый конфиг — [`configs/funnel-v3.json`](../configs/funnel-v3.json), версия 3. В нём есть `releaseNote`: «Adds a compliance branch, shortens variant B and introduces recommendation_expanded.» Ниже полный дифф: то, что перечислено в release note, и то, что в нём не упомянуто.

## Дифф v1 → v3

### Перечислено в release note

| # | Изменение | Детали |
|---|---|---|
| 1 | условная ветка compliance | в `priorities` новая опция `compliance` («Compliance and access control»). Новый шаг `security_constraints` (single-select: `standard`, `strict`, `regulated`) с `visibleWhen: priorities contains compliance`. В A стоит сразу после `priorities` (4-й вопрос), в B — тоже сразу после `priorities` (7-й) |
| 2 | экран удалён для B | `tool_count` убран из `stepSequence` варианта B; в A он остался |
| 3 | новое событие | `recommendation_expanded` со свойствами `result_id`, `action`, `source` |

### Не перечислено

| # | Изменение | Последствие |
|---|---|---|
| 4 | новый **обязательный** шаг `meeting_hours` (number, 0–40, шаг 1, «hours») в обоих вариантах: в A между `office_days` и `async_maturity`, в B вторым вопросом после `work_mode` | A стал длиннее: 7 обязательных вопросов вместо 6. B с учётом удалённого `tool_count` остался на 6 обязательных, как в v1. «Короче» он только относительно A v3 |
| 5 | два новых результата: `regulated_scale` (`priorities contains compliance` **и** `security_constraints in [strict, regulated]`) и `meeting_heavy` (`meeting_hours gte 15`). Оба стоят **первыми** в `resultRules` | при одинаковых ответах результат может отличаться от v1: например, удалённая команда с 20 часами встреч получит `meeting_heavy` вместо `async_native`. В синтетическом трафике `meeting_heavy` — самый частый результат v3 |
| 6 | новые операторы в условиях: `contains` (по multi-select) и `gte` (по числу); в v1 были только `eq` и `in` | движок поддерживает все операторы из [`src/shared/conditions.ts`](../src/shared/conditions.ts) |
| 7 | `experiment.id`: `question-order-and-result-framing-v1` → `…-v3` | это отдельный эксперимент; A/B сравнивается внутри версии |
| 8 | новые тексты B: интро (надзаголовок, заголовок, текст, кнопка), заголовок и подсказка `priorities`, заголовки всех результатов, CTA «Open the implementation details»; overrides B для двух новых результатов | см. [`experiment.md`](experiment.md#v3-question-order-and-result-framing-v3) |
| 9 | пропуск номера: 1 → 3, версии 2 нет | допустимо: правило — «номер больше всех сохранённых», а не «следующий по счёту» |
| 10 | в файле `status: "draft"` и новое поле `releaseNote` | `status` из файла игнорируется (жизненный цикл хранится в БД); `releaseNote` сохраняется в `funnel_versions.release_note` и показывается в админке |

Остальные шаги, результаты v1, события v1, TTL, настройки прогресса и приватности не изменились.

## Почему не нужны код и миграции

| Изменение | Чем покрыто |
|---|---|
| новые шаги и опции | `config.steps` и `stepSequence`; движок рендерит и валидирует шаг по его `type`; ответ становится новым ключом в `sessions.answers_json` |
| условная ветка | `visibleWhen` с оператором `contains`; прогресс считает условный шаг, пока условие неизвестно или истинно |
| удаление шага из B | `stepSequence` задаётся для каждого варианта |
| новые результаты и порядок правил | `resultRules` вычисляются по порядку на сервере |
| новое событие | белый список `events.allowed` закреплённой версии; таблица `events` универсальна |
| новый эксперимент | `experiment_id` хранится в сессии и событиях; аналитика группирует по версии |

Схема БД не меняется ([`data-model.md`](data-model.md#почему-схема-универсальная)).

Честная оговорка. Конфиг v3 лежал в репозитории с самого начала, и движок с контрактами проектировались с учётом обоих конфигов. Поэтому некоторые места кода уже знают о v3:

- операторы `contains` и `gte` реализованы заранее;
- имя `recommendation_expanded` прописано в коде. На сервере оно входит в список событий результата `RESULT_EVENTS` в [`routes/events.ts`](../src/server/routes/events.ts) (подстановка `step_id` шага результата) и в [`analytics.ts`](../src/server/analytics.ts) (событие считается достижением результата). На клиенте есть функция `recommendationExpanded()` в [`src/client/events.ts`](../src/client/events.ts), её вызывает обработчик CTA. Клиент отправляет событие, только если оно разрешено закреплённой версией, поэтому сессии v1 его не шлют.

Событие с любым другим новым именем сервер примет и сохранит по одному конфигу. Но чтобы клиент начал его отправлять, нужен код UI. А чтобы оно считалось достижением результата, имя нужно добавить в этот список.

## Публикация без передеплоя

Через `/admin`:

1. **Import fixture → `funnel-v3.json`.** Конфиг проходит `parseFunnelConfig`: zod-схему и семантические проверки (неизвестные шаги, условия на ответы, которые в каком-то варианте задаются позже, результат не последним шагом, повтор имени ответа внутри варианта и т. д.; проверки последовательностей идут по шагам после overrides варианта) и сохраняется как `draft`. Вместо фикстуры можно загрузить файл или вставить JSON.
2. **Проверка черновика.** Таблица версий и просмотр JSON (`GET /api/admin/versions/3`). Новые сессии в это время продолжают создаваться на v1.
3. **Publish v3.** Статус меняется на `published`, в журнал пишется `publish 3 from 1`, все новые сессии стартуют на v3.
4. **Проверка.** Быстрые ссылки на странице admin: `/?reset=1&variant=A` и `/?reset=1&variant=B`. В A выбор `compliance` открывает `security_constraints`, и счётчик вопросов растёт. В B нет `tool_count`, а `meeting_hours` идёт вторым. CTA на результате отправляет `recommendation_expanded`, и сервер его принимает. На dashboard появляются строки v3, а событие видно в таблице Events by name.
5. **Rollback.** Активной снова становится v1, v3 переходит в `rolled_back`.

То же через API (при заданном `ADMIN_TOKEN` с заголовком `x-admin-token`):

```bash
curl -X POST -H "x-admin-token: $ADMIN_TOKEN" $URL/api/admin/fixtures/funnel-v3.json/import
curl -X POST -H "x-admin-token: $ADMIN_TOKEN" $URL/api/admin/versions/3/publish
curl -X POST -H "x-admin-token: $ADMIN_TOKEN" $URL/api/admin/rollback
curl $URL/api/health   # { "ok": true, "activeVersion": 1 }
```

## Что происходит со старыми сессиями

| Ситуация | Поведение |
|---|---|
| сессия v1 была на середине, когда опубликовали v3 | `POST /api/sessions` с её id возвращает ту же сессию (`resumed: true`) с v1, тем же вариантом и `experiment_id`. Воронка собирается из сохранённого конфига v1 (`tool_count` есть, `meeting_hours` нет), результат считается по правилам v1 |
| у пользователя открыта вкладка с сессией v1 | клиент уже держит разрешённую воронку v1, а все запросы `/api/sessions/:id/*` разрешаются по закреплённой версии, поэтому ошибок нет |
| события сессии v1 | проверяются по списку v1: `recommendation_expanded` от неё отклоняется как `event_not_allowed`, но клиент v1 его и не отправляет |
| сессия v3 была на середине, когда сделали откат | продолжается на v3 до конца; `recommendation_expanded` по-прежнему принимается |
| события из outbox приходят после публикации или отката | принимаются по закреплённой версии сессии |
| сессия истекла (72 ч с создания) | клиент получает `410` (или, при перезагрузке страницы, сервер сразу выдаёт новую сессию) и показывает уведомление; новая сессия создаётся на активной версии |
| `?variant=` указывает другой вариант, чем у живой сессии | создаётся новая сессия: вариант существующей сессии не меняется |

Покрыто тестами в [`tests/pinning.test.ts`](../tests/pinning.test.ts) и [`tests/versions.test.ts`](../tests/versions.test.ts).

## Откат и сохранность аналитики

- Откат добавляет строку `rollback` в `activations` и меняет два статуса. Ни одна сессия и ни одно событие не удаляются ([`data-model.md`](data-model.md#версии-стек-активаций-и-статусы)).
- После отката dashboard по-прежнему показывает v1 и v3 рядом. Фильтр `version` разделяет их, у каждой версии своя карточка A/B.
- Откатанную версию можно снова сделать активной (`activate`), это шаг вперёд по тому же стеку.
- Повторный откат при одной версии на стеке возвращает `409 nothing_to_rollback`.

## Автоматическая репетиция

`npm run generate -- --scenario iteration2` проходит весь цикл через HTTP:

1. Первая волна сессий стартует на v1, треть из них останавливается после двух ответов.
2. Импорт и публикация v3.
3. Вторая волна сессий проходит v3.
4. Остановленные сессии возобновляются. Скрипт падает, если у них сменились версия или вариант.
5. Откат.

События отправляются в конце, уже после отката, так что заодно проверяется приём событий для откатанной v3.

Сценарий нужен на базе без v3. Генератор проверяет это через `/api/admin/overview` до создания сессий и, если v3 уже импортирована, останавливается с сообщением «Version 3 is already imported on this server, so the iteration2 scenario cannot run. Use --scenario simple.» Раньше он падал на импорте с `409` и оставлял сессии без событий.

Локальный прогон на чистой базе при интеграции (коммит `8c2f3ce`, 150 сессий, seed 42): `generate` печатает по строке на каждый этап (волна 1 на v1, импорт и публикация v3, волна 2 и возобновление, откат), а `verify` по его файлу ожидаемых агрегатов заканчивается так:

```
165/165 checks match the generator's ground truth for run <runId>.
```

Число проверок зависит от данных прогона: сколько строк распределения результатов и шагов воронок встретилось. Нынешний `verify` сверяет ещё и кампанию `(none)`, поэтому на тех же данных проверок было бы на одну больше.

Что видно на dashboard:

- `?version=3` — воронки v3 по вариантам. В A есть `meeting_hours` и `security_constraints`, в B нет `tool_count`. В таблице Events by name есть `recommendation_expanded`.
