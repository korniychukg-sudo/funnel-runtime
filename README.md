# Funnel Runtime

- **Публичный URL:** https://web-production-33e38.up.railway.app — воронка `/`, админка [`/admin`](https://web-production-33e38.up.railway.app/admin), аналитика [`/dashboard`](https://web-production-33e38.up.railway.app/dashboard)
- **Репозиторий:** https://github.com/korniychukg-sudo/funnel-runtime

Мини-платформа для запуска, версионирования и анализа многошаговых веб-воронок. Воронка целиком описана JSON-конфигом. Конфиг хранится на сервере как версия, и React-клиент рендерит её без захардкоженных экранов. За каждой сессией сервер закрепляет версию и вариант A/B. Он же ведёт навигацию, валидирует ответы и считает результат. События приходят пачками и дедуплицируются по `event_id`. Внутренний dashboard считает воронку, CTR, сравнение вариантов и версий по уникальным сессиям. Новая версия публикуется и откатывается из админки без передеплоя и без миграций БД. Стек: TypeScript, React 19 + Vite, Fastify 5, SQLite (`node:sqlite`), zod, vitest.

## A/B-гипотеза и основная метрика

- **v1.** Вариант B ставит первыми вопросы, от которых зависит результат (`work_mode`, затем `timezone_span`), подаёт интро через проблему, а результат — через действие, и обещает в CTA конкретный срок («See the 30-day action list»). Ожидание: меньше отвалов в начале и больше кликов по CTA.
- **v3.** Вариант B убирает `tool_count` (на результат он не влияет), ставит `meeting_hours` вторым вопросом и жёстче формулирует проблему. Ожидание: на одну точку отвала меньше и выше доля кликов.
- **Метрики.** Основная — **started → CTA**: уникальные сессии хотя бы с одним `cta_clicked` / начавшие сессии варианта. Вспомогательные — доля дошедших до результата (`resultRate`) и CTR CTA. Guardrail — отвал на первом вопросе.
- **Сравнение.** Двусторонний z-тест для двух долей с объединённой оценкой, α = 0.05. p-value считается, только если в каждом варианте ожидается не меньше 5 кликов и 5 не-кликов; иначе dashboard пишет «not enough data yet». Override-сессии (`?variant=`) исключены. Варианты сравниваются только внутри одной версии.

Подробно: [`docs/experiment.md`](docs/experiment.md).

## Быстрый старт

Нужен Node.js 22.13 или новее (`node:sqlite` без флага; см. `.nvmrc`).

```bash
npm ci

# режим разработки: Vite на :5173 проксирует /api на сервер :3000
npm run dev                 # → http://localhost:5173

# сборка как в проде: один процесс отдаёт API и статику
npm run build && npm start  # → http://localhost:3000
```

При первом запуске на пустой базе сервер импортирует `configs/funnel-v1.json` и делает v1 активной (действие `seed`). Предупреждение `ExperimentalWarning: SQLite is an experimental feature` ожидаемо.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `3000` | порт HTTP-сервера |
| `HOST` | `0.0.0.0` | адрес прослушивания (если задан `IP`, он важнее) |
| `DB_PATH` | `$RAILWAY_VOLUME_MOUNT_PATH/funnel.db`, если эта переменная задана, иначе `./data/funnel.db` | файл SQLite; каталог создаётся сам; `:memory:` для экспериментов |
| `ADMIN_TOKEN` | не задан | если задан, `/api/admin/*` требует заголовок `x-admin-token`, а `/admin` спрашивает токен; без него админка открыта |
| `CONFIGS_DIR` | `./configs` | откуда берутся фикстуры конфигов для импорта и seed |
| `STATIC_DIR` | `./dist/client`, если есть | собранный клиент; без него сервер отдаёт только API |

## Деплой

Публичный URL работает на Railway (trial, без карты):

- Один сервис. Railpack собирает репозиторий по [`railway.json`](railway.json): build `npm run build`, start `npm start`, healthcheck `/api/health`, `requiredMountPath: /data`, перезапуск при падении.
- Том 0.5 ГБ смонтирован в `/data`. На сервисе задано `DB_PATH=/data/funnel.db`.
- Путь к БД: `DB_PATH`; если он не задан — `$RAILWAY_VOLUME_MOUNT_PATH/funnel.db`; если нет и её — `./data/funnel.db`. Абсолютный путь пишется в лог один раз при старте (`Using database`, поле `dbPath`).
- База пережила передеплой: запись `seed` из первого деплоя осталась в журнале активаций.
- Приложение не делает исходящих запросов. От хостинга нужны только процесс и диск: внешней БД, сервиса аналитики или A/B нет.
- `ADMIN_TOKEN` на демо **намеренно не задан**, чтобы проверяющий сам мог публиковать, активировать и откатывать версии. В продакшне его нужно задать: тогда `/admin` спросит токен, а `/api/admin/*` без заголовка ответит `401`.

Другой хост подойдёт, если на нём есть Node 22.13+ и постоянный диск: `npm ci && npm run build`, затем `npm start`, `DB_PATH` на постоянный диск.

## Страницы и параметры

| Путь | Что это |
|---|---|
| `/` | воронка: сессия создаётся или восстанавливается автоматически |
| `/admin` | версии: импорт и загрузка конфигов, публикация, откат, повторная активация, журнал активаций, быстрые ссылки на новые сессии |
| `/dashboard` | аналитика: KPI, A/B по версиям, сравнение версий, воронки по шагам, распределение результатов, качество данных с таблицей событий по имени (Events by name), правила расчёта |

Параметры воронки (`/`):

- `?variant=A` или `?variant=B` — override варианта для QA. Работает только при создании сессии и только для существующего ключа варианта. Такая сессия помечается `assignment_source = override` и по умолчанию исключается из A/B-сравнения. Если в браузере уже есть живая сессия другого варианта, создаётся новая.
- `?reset=1` — забыть сессию этого браузера и начать новую.
- `utm_source`, `utm_medium`, `utm_campaign` — записываются в сессию при её создании (first touch) и проставляются во все её события.

Параметры dashboard синхронизируются с URL: `utm_campaign`, `version`, `run_id`, `include_overrides=1`. Значение `utm_campaign=(none)` выбирает сессии без кампании; в списке оно показано как «(no campaign)».

На публичном dashboard уже есть данные: прогоны генератора `run_id=prod-v1` и `prod-v3` и служебные сессии проверки второй итерации `prod-it2` ([`docs/iteration-2.md`](docs/iteration-2.md#ход-проверки-на-публичном-url)).

## Синтетический трафик

Сервер должен быть запущен (`npm run dev` или `npm start`).

```bash
# 150 сессий на активной версии
npm run generate -- --scenario simple --sessions 150 --seed 42

# сверить dashboard с «истиной» генератора (имя файла печатает generate)
npm run verify -- --expected expected-<runId>.json

# то же на публичном URL
npm run generate -- --base-url https://web-production-33e38.up.railway.app --run-id my-run
npm run verify -- --base-url https://web-production-33e38.up.railway.app --expected expected-my-run.json
```

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--base-url` | `http://localhost:3000` | адрес сервера (в dev-режиме тоже :3000) |
| `--sessions` | `150` | число сессий |
| `--seed` | `42` | seed модели поведения: ответы, отвалы, Back, сбои доставки. Вариант назначает сервер по случайному id сессии, а сессии идут параллельно, поэтому каждый прогон даёт свой набор данных. Каждый прогон сверяется со своим файлом ожидаемых агрегатов |
| `--run-id` | `gen-<seed>-<время>` | метка прогона; по ней фильтруется dashboard |
| `--scenario` | `simple` | `simple` или `iteration2` |
| `--admin-token` | `$ADMIN_TOKEN` | нужен для `iteration2`, если сервер защищён |
| `--concurrency`, `--out` | `6`, `expected-<runId>.json` | параллелизм и файл ожидаемых агрегатов |

Генератор ходит через настоящий HTTP API, так что вариант назначает сервер. Что попадает в трафик:

- пять источников UTM (четыре кампании и `direct` без кампании) и оба варианта;
- ветки `office_days` и, в v3, `security_constraints`;
- отвал на интро и на каждом вопросе, Back, повторные `step_viewed`, как при refresh;
- доставка пачками по 15–45 событий: часть пачек перемешана, соседние события переставлены, в пачки подмешаны копии уже отправленных событий;
- каждая шестая пачка отправляется повторно целиком;
- четыре заведомо некорректных события.

После отправки генератор сверяет ответы сервера (`accepted`, `duplicates`, `rejected`) со своим планом. Если симуляция оборвалась посередине, события уже начатых сессий всё равно доставляются.

`--scenario iteration2` проигрывает вторую итерацию:

1. Часть сессий стартует на активной версии, треть из них останавливается после двух ответов.
2. `funnel-v3.json` импортируется и публикуется.
3. Новые сессии проходят v3.
4. Остановленные сессии продолжаются. Скрипт падает, если у них сменились версия или вариант.
5. Выполняется откат.

Сценарию нужна база, где v3 ещё не импортирована, например `DB_PATH=./data/demo.db`. Генератор проверяет это до создания сессий и останавливается с понятным сообщением. На публичном URL v3 уже есть, там подходит только `simple`.

`verify` запрашивает `/api/analytics?run_id=…` и сверяет итоги, каждую версию и вариант, каждую строку каждой воронки (`reached`, `progressed`, `dropped`), распределение результатов, показатели качества данных и фильтр по каждой кампании, включая `(none)`. Подробнее в [`docs/analytics.md`](docs/analytics.md#проверка-по-генератору). Чтобы A/B-эффект стал статистически значимым, нужно около 2000 сессий ([`docs/experiment.md`](docs/experiment.md)).

## Как выполнены требования

| § | Требование | Как сделано | Где |
|---|---|---|---|
| 1 | Динамическая воронка | Клиент получает от сервера разрешённую воронку своей версии и варианта и рендерит шаг по `type`: `info`, `single-select`, `multi-select`, `number`, `result`. Ветвления задаются через `visibleWhen` (операторы `eq` … `answered`, комбинаторы `all`/`any`/`not`). Валидация одна и та же (`validateAnswer`) на клиенте и на сервере. Прогресс считает только доступные шаги. Состояние хранится на сервере, id сессии лежит в `localStorage`, поэтому refresh, Back и повторное открытие возвращают тот же шаг с ответами. | [`src/shared/engine.ts`](src/shared/engine.ts), [`src/shared/conditions.ts`](src/shared/conditions.ts), [`src/client/funnel/`](src/client/funnel), [`src/server/routes/sessions.ts`](src/server/routes/sessions.ts) |
| 2 | Версии и откаты | Конфиги хранятся в `funnel_versions`, история активаций — в append-only `activations` (стек). Публикация, откат и повторная активация делаются из `/admin`. Сессия закрепляет версию при создании, новые сессии получают только активную версию. | [`src/server/versions.ts`](src/server/versions.ts), [`src/client/pages/AdminPage.tsx`](src/client/pages/AdminPage.tsx), [`docs/data-model.md`](docs/data-model.md) |
| 3 | A/B | Вариант назначает сервер: `sha256(experimentId:sessionId)` раскладывается по весам. Вариант пишется в сессию и не меняется. Override задаётся через `?variant=`. Вариант меняет тексты (`stepOverrides`), порядок и состав шагов (`stepSequence`) и экран результата (`resultOverrides`). Гипотеза и метрика — [выше](#ab-гипотеза-и-основная-метрика). | [`src/server/assignment.ts`](src/server/assignment.ts), [`docs/experiment.md`](docs/experiment.md) |
| 4 | События | `POST /api/events` принимает пачку до 500 событий в одной транзакции и возвращает статус по каждому элементу. Дубли отсекает `INSERT OR IGNORE` по `event_id`. Контекст и UTM берутся из сессии. Свойства фильтруются по белому списку конфига и проверяются по значению, `step_type` и `answer_kind` ставит сервер. На клиенте работает outbox в `localStorage` с повторами и отправкой при уходе со страницы. | [`src/server/routes/events.ts`](src/server/routes/events.ts), [`src/client/outbox.ts`](src/client/outbox.ts), [`docs/events.md`](docs/events.md) |
| 5 | Dashboard | Чистая функция `computeAnalytics` считает по множествам уникальных сессий: начавшие, конверсия и отвал по шагам, результат, CTR, A/B с z-тестом, версии, события по имени. Фильтры: `utm_campaign` (включая `(none)`), `version`, `run_id`. | [`src/server/analytics.ts`](src/server/analytics.ts), [`src/client/pages/DashboardPage.tsx`](src/client/pages/DashboardPage.tsx), [`docs/analytics.md`](docs/analytics.md) |
| 6 | Генератор | `npm run generate` (150 сессий по умолчанию) и `npm run verify`, который сверяет dashboard с ground truth. | [`scripts/`](scripts) |
| 7 | Технические условия | TypeScript на клиенте, сервере, в скриптах и тестах. React, Fastify на Node 22, SQLite в файле, один репозиторий, без внешних сервисов. | [`package.json`](package.json), [`tests/`](tests) |
| 8 | Вторая итерация | v3 импортируется из `configs/` кнопкой в `/admin` и публикуется без изменений кода и схемы. Старые сессии остаются на v1. Откат делается одной кнопкой, аналитика сохраняется. Проверено на публичном URL. | [`docs/iteration-2.md`](docs/iteration-2.md), [`tests/pinning.test.ts`](tests/pinning.test.ts) |

## Архитектура

```
configs/*.json ──импорт──▶ funnel_versions (SQLite)
                                 │ config по закреплённой версии
src/shared (схема конфига, условия, движок) ◀── браузер: рендер, прогресс, мгновенная валидация
                                            ◀── сервер: навигация, валидация, результат, приём событий
                                            ◀── генератор: симуляция сессий и ожидаемые агрегаты
```

- **Один движок на троих.** `src/shared/engine.ts` (видимость шагов, следующий и предыдущий шаг, прогресс, валидация, результат) используют браузер, сервер и генератор. В `src/shared` нет API Node и DOM.
- **Сервер — источник истины.** Он хранит ответы и текущий шаг, проверяет, что шаг доступен (`canNavigateTo`), и сам считает результат. Клиент только показывает состояние и отправляет события.
- **Схема БД не зависит от воронки.** Конфиг, ответы и свойства событий лежат в JSON-колонках, имена шагов и событий — строки. Новые шаги, результаты и события миграций не требуют ([`docs/data-model.md`](docs/data-model.md)).
- **Аналитика — чистая функция** от строк сессий и событий, поэтому она тестируется без HTTP.
- Контракты между частями зафиксированы в [`docs/contracts.md`](docs/contracts.md).

## Допущения и известные ограничения

- Сессия живёт `ttlHours` (72 ч) с момента создания и не продлевается. После истечения клиент получает новую сессию на активной версии и видит уведомление. Ответы истёкших сессий обнуляются раз в час, события остаются.
- Сессия привязана к браузеру через `localStorage`: вкладки одного браузера делят одну сессию.
- Создание сессии не идемпотентно: если ответ на `POST /api/sessions` потерялся и клиент повторил запрос, появится вторая сессия, и первая будет считаться отвалом на интро.
- UTM записываются по first touch, при создании сессии. UTM, присланные в событиях, игнорируются. Кампанию с буквальным именем `(none)` нельзя выбрать фильтром: `utm_campaign=(none)` выбирает только сессии без кампании, а отдельным пунктом в списке кампаний это имя не показывается.
- Override-сессии исключаются только из A/B-сравнения. В итогах, сравнении версий и воронках они учитываются.
- Условный шаг засчитывается достигнутым только по его собственным событиям: сырых ответов в аналитике нет, а восстановить видимость шага без них нельзя.
- Значимость считается двусторонним z-тестом без поправок на подглядывание и множественные сравнения.
- Аналитика пересчитывается в памяти по всем событиям при каждом запросе. Для демо-объёмов этого хватает (2000 сессий ≈ 40 тыс. событий), для продакшна нужны предагрегаты.
- Один процесс и один файл SQLite: нужен постоянный диск, горизонтального масштабирования нет.
- Черновик версии нельзя изменить или удалить. Исправление загружается как новая версия с большим номером. Номер берётся из самого конфига и должен быть больше всех сохранённых.
- Админка на демо открыта намеренно (`ADMIN_TOKEN` не задан): кто угодно с URL может публиковать и откатывать версии. `/dashboard` и `GET /api/analytics` открыты всегда (отдают только агрегаты). Rate limiting на `/api/sessions` и `/api/events` нет.
- Свойства `action` и `source` проверяются только по типу (примитив или строка до 256 символов), `visible_step_index` и `visible_step_count` — только как `null` или неотрицательное целое. `result_id`, `next_step_id` и `destination_step_id` сверяются с конфигом и сессией, `step_type` и `answer_kind` ставит сервер ([`docs/events.md`](docs/events.md#приём-пачки)).
- При уходе со страницы outbox отправляет одним keepalive-запросом не больше 50 событий. Остальные остаются в `localStorage` и уйдут при следующем открытии сайта в этом браузере; если пользователь не вернётся, они потеряются.
- В текущем UI основной CTA сразу раскрывает список рекомендаций, поэтому в v3 `cta_clicked` и `recommendation_expanded` отправляются одним кликом.
- Seed генератора фиксирует модель поведения, но не набор данных: варианты назначает сервер, поэтому каждый прогон даёт свои числа.
- Railway trial действует 30 дней с 2026-10-02, затем аккаунт переходит на Free plan ($1 кредита в месяц), и постоянно работающий сервис может остановиться, когда кредит кончится.
- Доступность из некоторых российских сетей может зависеть от IP edge-узла Railway: при исследовании хостинга часть edge-адресов Railway не отвечала с российских узлов проверки.
