# Funnel Runtime

Мини-платформа для запуска, версионирования и анализа многошаговых веб-воронок. Воронка целиком описана JSON-конфигом. Конфиг хранится на сервере как версия, и React-клиент рендерит её без захардкоженных экранов. За каждой сессией сервер закрепляет версию и вариант A/B. Он же ведёт навигацию, валидирует ответы и считает результат. События приходят пачками и дедуплицируются по `event_id`. Внутренний dashboard считает воронку, CTR, сравнение вариантов и версий по уникальным сессиям. Новая версия публикуется и откатывается из админки без передеплоя и без миграций БД. Стек: TypeScript, React 19 + Vite, Fastify 5, SQLite (`node:sqlite`), zod, vitest.

## Быстрый старт

Нужен Node.js 22.13 или новее (`node:sqlite` без флага; см. `.nvmrc`).

```bash
npm ci

# режим разработки: Vite на :5173 проксирует /api на сервер :3000
npm run dev                 # → http://localhost:5173

# сборка как в проде: один процесс отдаёт API и статику
npm run build && npm start  # → http://localhost:3000
```

При первом запуске на пустой базе сервер импортирует `configs/funnel-v1.json` и делает v1 активной (действие `seed`). Предупреждение `ExperimentalWarning: SQLite is an experimental feature` ожидаемо.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `3000` | порт HTTP-сервера |
| `HOST` | `0.0.0.0` | адрес прослушивания (если задан `IP`, он важнее) |
| `DB_PATH` | `./data/funnel.db` | файл SQLite; каталог создаётся сам; `:memory:` для экспериментов |
| `ADMIN_TOKEN` | не задан | если задан, `/api/admin/*` требует заголовок `x-admin-token`; без него админка открыта (локальная разработка) |
| `CONFIGS_DIR` | `./configs` | откуда берутся фикстуры конфигов для импорта и seed |
| `STATIC_DIR` | `./dist/client`, если есть | собранный клиент; без него сервер отдаёт только API |

Деплой: нужен хост с Node 22.13+ и постоянным диском под SQLite. Сборка `npm ci && npm run build`, старт `npm start`, healthcheck `GET /api/health`. `DB_PATH` должен указывать на постоянный диск (например, `/data/funnel.db`), и стоит задать `ADMIN_TOKEN`. `railway.json` описывает такую конфигурацию (том `/data`).

## Страницы и параметры

| Путь | Что это |
|---|---|
| `/` | воронка: сессия создаётся или восстанавливается автоматически |
| `/admin` | версии: импорт и загрузка конфигов, публикация, откат, повторная активация, журнал активаций, быстрые ссылки на новые сессии |
| `/dashboard` | аналитика: KPI, A/B по версиям, сравнение версий, воронки по шагам, распределение результатов, качество данных, правила расчёта |

Параметры воронки (`/`):

- `?variant=A` или `?variant=B` — override варианта для QA. Работает только при создании сессии и только для существующего ключа варианта. Такая сессия помечается `assignment_source = override` и по умолчанию исключается из A/B-сравнения. Если в браузере уже есть живая сессия другого варианта, создаётся новая.
- `?reset=1` — забыть сессию этого браузера и начать новую.
- `utm_source`, `utm_medium`, `utm_campaign` — записываются в сессию при её создании (first touch) и проставляются во все её события.

Параметры dashboard синхронизируются с URL: `utm_campaign`, `version`, `run_id`, `include_overrides=1`.

## Синтетический трафик

Сервер должен быть запущен (`npm run dev` или `npm start`).

```bash
# 150 сессий на активной версии
npm run generate -- --scenario simple --sessions 150 --seed 42

# сверить dashboard с «истиной» генератора (имя файла печатает generate)
npm run verify -- --expected expected-<runId>.json
```

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--base-url` | `http://localhost:3000` | адрес сервера (в dev-режиме тоже :3000) |
| `--sessions` | `150` | число сессий |
| `--seed` | `42` | seed PRNG: тот же seed даёт те же ответы и тот же план доставки событий |
| `--run-id` | `gen-<seed>-<время>` | метка прогона; по ней фильтруется dashboard |
| `--scenario` | `simple` | `simple` или `iteration2` |
| `--admin-token` | `$ADMIN_TOKEN` | нужен для `iteration2`, если сервер защищён |
| `--concurrency`, `--out` | `6`, `expected-<runId>.json` | параллелизм и файл ожидаемых агрегатов |

Генератор ходит через настоящий HTTP API, так что вариант назначает сервер. Что попадает в трафик:

- пять источников UTM (четыре кампании и `direct` без кампании) и оба варианта;
- ветки `office_days` и, в v3, `security_constraints`;
- отвал на интро и на каждом вопросе, Back, повторные `step_viewed`, как при refresh;
- доставка пачками по 15–45 событий: часть пачек перемешана, соседние события переставлены, в пачки подмешаны копии уже отправленных событий;
- каждая шестая пачка отправляется повторно целиком;
- четыре заведомо некорректных события.

После отправки генератор сверяет ответы сервера (`accepted`, `duplicates`, `rejected`) со своим планом.

`--scenario iteration2` проигрывает вторую итерацию:

1. Часть сессий стартует на активной версии, треть из них останавливается после двух ответов.
2. `funnel-v3.json` импортируется и публикуется.
3. Новые сессии проходят v3.
4. Остановленные сессии продолжаются. Скрипт падает, если у них сменились версия или вариант.
5. Выполняется откат.

Сценарий нужно запускать на базе, где v3 ещё не импортирована, например `DB_PATH=./data/demo.db`. Иначе импорт вернёт `409 version_exists`.

`verify` запрашивает `/api/analytics?run_id=…` и сверяет итоги, каждую версию и вариант, каждую строку каждой воронки (`reached`, `progressed`, `dropped`), распределение результатов, показатели качества данных и фильтр по каждой кампании. Подробнее в [`docs/analytics.md`](docs/analytics.md#проверка-по-генератору). Чтобы A/B-эффект стал статистически значимым, нужно около 2000 сессий ([`docs/experiment.md`](docs/experiment.md)).

## Как выполнены требования

| § | Требование | Как сделано | Где |
|---|---|---|---|
| 1 | Динамическая воронка | Клиент получает от сервера разрешённую воронку своей версии и варианта и рендерит шаг по `type`: `info`, `single-select`, `multi-select`, `number`, `result`. Ветвления задаются через `visibleWhen` (операторы `eq` … `answered`, комбинаторы `all`/`any`/`not`). Валидация одна и та же (`validateAnswer`) на клиенте и на сервере. Прогресс считает только доступные шаги. Состояние хранится на сервере, id сессии лежит в `localStorage`, поэтому refresh, Back и повторное открытие возвращают тот же шаг с ответами. | [`src/shared/engine.ts`](src/shared/engine.ts), [`src/shared/conditions.ts`](src/shared/conditions.ts), [`src/client/funnel/`](src/client/funnel), [`src/server/routes/sessions.ts`](src/server/routes/sessions.ts) |
| 2 | Версии и откаты | Конфиги хранятся в `funnel_versions`, история активаций — в append-only `activations` (стек). Публикация, откат и повторная активация делаются из `/admin`. Сессия закрепляет версию при создании, новые сессии получают только активную версию. | [`src/server/versions.ts`](src/server/versions.ts), [`src/client/pages/AdminPage.tsx`](src/client/pages/AdminPage.tsx), [`docs/data-model.md`](docs/data-model.md) |
| 3 | A/B | Вариант назначает сервер: `sha256(experimentId:sessionId)` раскладывается по весам. Вариант пишется в сессию и не меняется. Override задаётся через `?variant=`. Вариант меняет тексты (`stepOverrides`), порядок и состав шагов (`stepSequence`) и экран результата (`resultOverrides`). | [`src/server/assignment.ts`](src/server/assignment.ts), [`docs/experiment.md`](docs/experiment.md) |
| 4 | События | `POST /api/events` принимает пачку до 500 событий в одной транзакции и возвращает статус по каждому элементу. Дубли отсекает `INSERT OR IGNORE` по `event_id`. Контекст и UTM берутся из сессии, свойства фильтруются по белому списку конфига. На клиенте работает outbox в `localStorage` с повторами. | [`src/server/routes/events.ts`](src/server/routes/events.ts), [`src/client/outbox.ts`](src/client/outbox.ts), [`docs/events.md`](docs/events.md) |
| 5 | Dashboard | Чистая функция `computeAnalytics` считает по множествам уникальных сессий: начавшие, конверсия и отвал по шагам, результат, CTR, A/B с z-тестом, версии. Фильтры: `utm_campaign`, `version`, `run_id`. | [`src/server/analytics.ts`](src/server/analytics.ts), [`src/client/pages/DashboardPage.tsx`](src/client/pages/DashboardPage.tsx), [`docs/analytics.md`](docs/analytics.md) |
| 6 | Генератор | `npm run generate` (150 сессий по умолчанию) и `npm run verify`, который сверяет dashboard с ground truth. | [`scripts/`](scripts) |
| 7 | Технические условия | TypeScript на клиенте, сервере, в скриптах и тестах. React, Fastify на Node 22, SQLite в файле, один репозиторий, без внешних сервисов. | [`package.json`](package.json), [`tests/`](tests) |
| 8 | Вторая итерация | v3 импортируется из `configs/` кнопкой в `/admin` и публикуется без изменений кода и схемы. Старые сессии остаются на v1. Откат делается одной кнопкой, аналитика сохраняется. | [`docs/iteration-2.md`](docs/iteration-2.md), [`tests/pinning.test.ts`](tests/pinning.test.ts) |

## Архитектура

```
configs/*.json ──импорт──▶ funnel_versions (SQLite)
                                 │ config по закреплённой версии
src/shared (схема конфига, условия, движок) ◀── браузер: рендер, прогресс, мгновенная валидация
                                            ◀── сервер: навигация, валидация, результат, приём событий
                                            ◀── генератор: симуляция сессий и ожидаемые агрегаты
```

- **Один движок на троих.** `src/shared/engine.ts` (видимость шагов, следующий и предыдущий шаг, прогресс, валидация, результат) используют браузер, сервер и генератор. В `src/shared` нет API Node и DOM.
- **Сервер — источник истины.** Он хранит ответы и текущий шаг, проверяет, что шаг доступен (`canNavigateTo`), и сам считает результат. Клиент только показывает состояние и отправляет события.
- **Схема БД не зависит от воронки.** Конфиг, ответы и свойства событий лежат в JSON-колонках, имена шагов и событий — строки. Новые шаги, результаты и события миграций не требуют ([`docs/data-model.md`](docs/data-model.md)).
- **Аналитика — чистая функция** от строк сессий и событий, поэтому она тестируется без HTTP.
- Контракты между частями зафиксированы в [`docs/contracts.md`](docs/contracts.md).

## Допущения и известные ограничения

- Сессия живёт `ttlHours` (72 ч) с момента создания и не продлевается. После истечения клиент получает новую сессию на активной версии. Ответы истёкших сессий обнуляются раз в час, события остаются.
- Сессия привязана к браузеру через `localStorage`: вкладки одного браузера делят одну сессию.
- UTM записываются по first touch, при создании сессии. UTM, присланные в событиях, игнорируются.
- Override-сессии исключаются только из A/B-сравнения. В итогах, сравнении версий и воронках они учитываются.
- Условный шаг засчитывается достигнутым только по его собственным событиям: сырых ответов в аналитике нет, а восстановить видимость шага без них нельзя.
- Значимость считается двусторонним z-тестом без поправок на подглядывание и множественные сравнения.
- Аналитика пересчитывается в памяти по всем событиям при каждом запросе. Для демо-объёмов этого хватает (2000 сессий ≈ 40 тыс. событий), для продакшна нужны предагрегаты.
- Один процесс и один файл SQLite: нужен постоянный диск, горизонтального масштабирования нет.
- Черновик версии нельзя изменить или удалить. Исправление загружается как новая версия с большим номером. Номер берётся из самого конфига и должен быть больше всех сохранённых.
- `/dashboard` и `GET /api/analytics` открыты без токена (отдают только агрегаты). `/api/admin/*` закрыт, если задан `ADMIN_TOKEN`. Rate limiting на `/api/sessions` и `/api/events` нет.
- Белый список свойств событий проверяет ключи, но не значения.
- В текущем UI основной CTA сразу раскрывает список рекомендаций, поэтому в v3 `cta_clicked` и `recommendation_expanded` отправляются одним кликом.
- Конфиг v3 был в репозитории с самого начала, и движок проектировался с учётом обоих конфигов. Что из этого следует, описано в [`docs/iteration-2.md`](docs/iteration-2.md#почему-не-нужны-код-и-миграции).
- Тексты воронки, admin и dashboard на английском, как и в выданных конфигах (`locale: en-AU`).
